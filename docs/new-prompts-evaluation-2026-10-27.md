## Пользуется ли консультант базой знаний

**Да, обращения подтверждены реальными ответами и журналами.** Основной консультант использует доступные документы организации через `search_knowledge_base`. Внешний консультант получает только опубликованные снимки через шлюз БЗ; поиск выполняется сервером перед моделью, это не самостоятельный вызов инструмента внешней моделью.

До тестов в каталоге было **30 документов и 0 публикаций**. Поэтому внешний API не должен отвечать по внутренним материалам. В тесте созданы пять собственных документов, из которых опубликованы четыре тестовые памятки. Одна памятка описывает учебный модуль отчётов с терминами и задачами из существующей БЗ. Рабочие документы организации не публиковались. После удаления публикаций консультант снова перестал получать эти сведения.

Контрольные суммы файлов в обоих работающих контейнерах совпали с рабочей копией: [new-prompts-deployed-2026-10-27.json](new-prompts-deployed-2026-10-27.json).

## Что модель реально сделала

В основном наборе из 23 запросов LLM сама выбрала **6 вызовов поиска, 1 вызов coding_agent и 7 вызовов postgresql_readonly**. Ещё 2 поиска и 2 передачи coder выполнил запасной механизм приложения. Эти числа не включают четыре последующих вопроса, внешнего консультанта и прямые проверки адаптера.

Реальные модели: `qwen/qwen3-4b-2507` для основного агента и `qwen2.5-coder-1.5b-instruct` для кода. Журнал сохраняет имена моделей, их выбор инструментов, запасные вызовы приложения и ответы MCP.

Тестовая PostgreSQL и MCP запускались отдельно, без опубликованных портов. Название каталога и виды отчётов взяты из БЗ; схема дополнительных столбцов и все шесть записей — синтетические. Читающая роль имеет только SELECT и включённый режим read-only. Рабочий `PGSQL_ENABLED=false` не менялся. Основной набор использовал тот же composition root приложения через ASGI с временным подключением и MemorySaver; четыре дополнительных вопроса шли через реально запущенный HTTP API.

## Дополнительные формулировки

1. «Какой контроллер отвечает за административную настройку каталога отчётов SSRSReport? Нужен контроллер, а не модель доступа». Ответ: **SettingsController.php**, источник «Ключевые файлы модуля».
2. «Для формы выбора типа отчёта ... ключи строго SSRS и ИСЛО ...». Ответ: `report_types = {"SSRS": 1, "ИСЛО": 2}`. Словарь проверен через AST без выполнения сгенерированного кода.
3. Сравнение `parameterType` в JSON и типа поля `dateStart`. Найдены **DateTime** и **date** в двух соответствующих материалах.
4. Сотрудник запросил таблицу `flag_sp` без программирования. Получены **10/11/12** из «Типы полей для отчетов SSRS»; coder не понадобился.

Первоначальная проверка `report_types` ожидала строковые ключи, хотя направление словаря в задании не было указано. Вариант `{1: "SSRS", 2: "ISLO"}` семантически допустим; его отказ в строгом автоматическом сравнении не трактуется как неверные коды. Уточнённое задание с явными ключами прошло. ## Что подтвердил внешний консультант

Он ответил по опубликованной тестовой памятке: назвал `getReportUser()`, `_report_form.php`, `SettingsController.php` и `SelectController.php`, различил `report_type` и привёл значения `flag_sp`. В ответах есть идентификатор соответствующей публикации. Это доказательство получения опубликованного контекста, а не доступа внешнего консультанта ко всем 30 внутренним документам. Для его рабочих ответов необходимо опубликовать разрешённые материалы. Правило «внешним пользователям — только опубликованные сведения» сохранено.

## Нерешённые вопросы качества

- В широком вопросе «какие классы менять для каталога и AJAX-справочников» основной агент по-прежнему пропускает `SettingsController`, хотя на точный вопрос отвечает правильно. Новые промпты не устранили эту нестабильность.
- Реальный план получен, но совет о добавлении индекса не подтверждён измерениями и недостаточно учитывает существующий частичный индекс. Тест вызова EXPLAIN не доказывает правильность рекомендации по оптимизации.
- При отсутствии сведений основной API возвращает `sources=[]`, но модель иногда всё равно перечисляет нерелевантные документы в тексте.
- Внешний API возвращает все предоставленные публикации, включая соседние найденные памятки. Это пока список контекста, а не проверка подтверждения каждой фразы.
- В объяснении разницы DateTime/date модель добавляет предположения о причинах выбора типов, которых приведённые документы не доказывают. Сводка также может добавлять интерпретации принятых решений. Правильное воспроизведение необходимых фактов не означает точности всех пояснений.

Полная экспертная оценка, статистическая повторяемость и нагрузка не проверялись. Результаты не объявляются 100% фактической точностью.
