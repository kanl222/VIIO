# Решения для ошибок маршрутизации и ответов VIIO

Исследование официальной документации, 27 октября 2026. Основание: [живая проверка VIIO](system-evaluation-2026-10-27.md) и `APIAgent/src/apiagent/services/coding_agent.py`. Приложение не изменялось. Ниже предложения для проверки, а не обещание устранить все ошибки модели.

## 1. Вычислять арифметику программно

LangGraph различает workflow с заранее заданными переходами и агента, который сам выбирает действия. В документации есть пример обычной функции умножения как инструмента. Для воспроизводимой ошибки `17 × 23 → 401` подходит именно вычисление обычной функцией. [Официальные workflows и инструменты](https://docs.langchain.com/oss/python/langgraph/workflows-agents).

Предложение для VIIO: распознавать ограниченную грамматику арифметических выражений на сервере, вычислять через разрешённые операции и возвращать результат напрямую. Не использовать `eval`, запуск Python, файлы или shell. Ограничить длину выражения, глубину, размер чисел и показатели степени; обрабатывать деление на ноль. Это сохраняет требование «coder только пишет код»: вычисляет сервер общего ассистента, у coder инструменты не появляются. Обычный LLM tool-call необязателен: маленькая модель может вообще не вызвать вычислитель.

Граница: числовые задачи на естественном языке потребуют отдельного извлечения и проверки выражения. Верный вычислитель не гарантирует правильный перевод условия задачи.

## 2. Установить явный порядок маршрутов

В текущем коде отказ от генерации кода подавляет coder только при `needs_knowledge(message)`. Поэтому фраза «изменения структуры…Код не нужен» всё ещё совпадает с широким шаблоном. Это локальная причина, подтверждаемая кодом; установка нового фреймворка не требуется.

Рекомендуемый порядок: команды пользователя → проверка роли → отрицание генерации кода → продолжение активной задачи → явные технические признаки → общий ответ. Для противоречия `/code` и «код не нужен» предусмотреть уточнение либо документированный приоритет команды. Учитывать различие «не пиши код, объясни алгоритм» и «код рецепта»: разрешение на объяснение технической темы не равнозначно разрешению на генерацию кода.

Для остаточной неоднозначности возможен классификатор с ограниченным набором меток, но он добавляет задержку и сам нуждается в тестах. LangChain поддерживает структурированный вывод; `ToolStrategy` требует tool-calling, а `ProviderStrategy` — поддержки формата провайдером. Поэтому нельзя автоматически навязывать их текущему coder без tools. [Structured output](https://docs.langchain.com/oss/python/langchain/structured-output).

## 3. Сохранять активную специализацию беседы

Официальный шаблон handoffs сохраняет `active_agent`/`current_step` между сообщениями. Применительно к VIIO: хранить `active_specialist=coder`, последний артефакт и краткую цель в состоянии беседы; «добавь проверку отрицательных значений» направлять в существующую историю coder. Это не требует, чтобы coder сам вызывал handoff: переход может выполнять сервер. [Handoffs](https://docs.langchain.com/oss/python/langchain/multi-agent/handoffs).

Права перепроверять при каждом запросе, включая продолжения; состояние специализации не даёт доступа. Явная новая тема или команда переключает маршрут. Нельзя бессрочно отправлять все сообщения беседы в coder только потому, что однажды был код. Нужны проверки переходов «код → уточнение → новая общая тема», смены роли и перезапуска.

## 4. Отделить преобразование текста от ответа по документам

LangChain описывает управление контекстом отдельного вызова: инструкции, история, инструменты и формат ответа можно менять в зависимости от задачи. Избыточные инструменты и контекст могут увеличивать ошибки. [Context engineering](https://docs.langchain.com/oss/python/langchain/context-engineering).

Предложение: отдельные короткие шаблоны `rewrite`, `general`, `knowledge_qa`, `coding`. Для `rewrite` передавать исходную фразу и правила: сохранить речевое действие, факты и срок; выдать ровно одно предложение. Пример пары «пришли отчёт сегодня» → «Пожалуйста, пришлите отчёт сегодня» объясняет ожидаемое поведение. KB и инструкции об источниках этой задаче не нужны. Явные инструкции и few-shot-примеры рекомендуются официальным руководством Google; перенос на Qwen — проверяемая гипотеза, а не доказанное улучшение. [Prompt design](https://ai.google.dev/gemini-api/docs/prompting-strategies).

## 5. Источники оформлять из серверных метаданных

LangChain `Document` хранит текст отдельно от `metadata` и `id`; метаданные могут содержать источник. [Document и источник](https://docs.langchain.com/oss/python/langchain/knowledge-base).

Для VIIO сохранять разрешённые `doc_id`, название и фрагмент отдельно от строкового промпта. Coder выдаёт код; сервер добавляет «Предоставленные материалы» из реально переданного набора. Нельзя автоматически называть все найденные документы доказательством каждого утверждения. Если нужны точные цитаты по утверждениям, модель возвращает идентификаторы, сервер проверяет их принадлежность набору и наличие фрагмента. Одна проверка ID не доказывает смысловую поддержку. Это наше инженерное предложение на основе документированных метаданных; готовой гарантии достоверности цитирования здесь нет.

## 6. Проверить точную разновидность Qwen

Официальная карточка `Qwen3-4B-Instruct-2507` указывает: только non-thinking; рекомендует sampling `temperature=0.7`, `top_p=0.8`, `top_k=20`, `min_p=0`. Сначала нужно подтвердить, что серверный псевдоним `qwen/qwen3-4b-2507` действительно соответствует этой модели. Переключатель `/think` не является решением для Instruct-2507. Рекомендации sampling — исходная точка сравнительного прогона, не исправление арифметики. [Карточка Qwen](https://huggingface.co/Qwen/Qwen3-4B-Instruct-2507).

Приоритет внедрения: точные маршруты и вычислитель → состояние coder → отдельный rewrite → серверные источники. После каждого шага повторять исходные неуспешные сценарии и соседние отрицательные примеры. Более сложный агент или большая модель не заменяет исправления подтверждённых ошибок серверной логики.
