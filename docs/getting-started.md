# VIIO: запуск, пользователи и загрузка документов

Инструкция для текущего Docker Compose из корня проекта. Обновлена 26.10.2026 по конфигурации и исходному коду. Windows-команды предназначены для PowerShell, Linux-команды — для Bash. Установка на чистой Linux-машине в рамках обновления документации не выполнялась.

## 1. Что подготовить

- Исходники VIIO на компьютере. В корне должны быть `docker-compose.yml`, `.env.example`, каталоги `assistent`, `WebChat` и `init-db`.
- Windows: [Docker Desktop](https://docs.docker.com/desktop/setup/install/windows-install/) с Linux-контейнерами и поддержкой WSL 2. Запустите Docker Desktop до выполнения команд.
- Linux: [Docker Engine](https://docs.docker.com/engine/install/) и [плагин Docker Compose](https://docs.docker.com/compose/install/linux/). Команды ниже предполагают доступ к Docker от текущего пользователя; при необходимости запускайте их через `sudo`.
- Локальный сервер моделей LM Studio или Ollama, работающий вне контейнеров VIIO.

При запуске через Docker отдельно устанавливать Python, Node.js, PostgreSQL и Qdrant на хост не требуется. Первая сборка требует интернета для загрузки образов и зависимостей.

## 2. Подготовить модели

### LM Studio

1. Установите LM Studio и загрузите модель для диалога и модель эмбеддингов.
2. В разделе сервера запустите OpenAI-совместимый API на порту `1234`.
3. Убедитесь, что сервер доступен из Docker. На Linux он должен слушать адрес, доступный с Docker bridge, а не только `127.0.0.1`; например, `0.0.0.0`. Ограничьте доступ к порту сетью, из которой обращается VIIO.
4. Запишите точные API-идентификаторы загруженных моделей в `.env`. Их можно проверить через `GET http://localhost:1234/v1/models`.

Настройки из примера:

```dotenv
LLM_PROVIDER=lmstudio
LMSTUDIO_BASE_URL=http://host.docker.internal:1234/v1
LMSTUDIO_MODEL=qwen/qwen3-4b-2507
LMSTUDIO_EMBEDDING_MODEL=text-embedding-nomic-embed-text-v1.5
CODING_AGENT_ENABLED=true
CODING_MODEL=qwen2.5-coder-1.5b-instruct
CODING_ALLOWED_ROLES=["programmer","admin"]
```

Это примеры имён: укажите модели, которые действительно доступны на вашем сервере. Модель консультанта должна поддерживать вызов инструментов; coder использует только текстовую генерацию. Если `CODING_MODEL` пуст, используется модель консультанта. Для отдельного coder задайте его имя явно и обеспечьте доступность обеих моделей на сервере.

### Ollama

В `.env` переключите провайдера и укажите доступные модели:

```dotenv
LLM_PROVIDER=ollama
OLLAMA_BASE_URL=http://host.docker.internal:11434
OLLAMA_MODEL=llama3.1
OLLAMA_EMBEDDING_MODEL=nomic-embed-text
CODING_MODEL=
```

Ollama также должен быть доступен из контейнера, включая привязку к доступному сетевому адресу. При выборе отдельного coder укажите в `CODING_MODEL` имя модели именно из Ollama.

В Compose уже есть сопоставление `host.docker.internal:host-gateway` для assistent, в том числе для Linux. `localhost` внутри контейнера указывает на сам контейнер, поэтому для сервера моделей на хосте его использовать не нужно. [Сеть Docker Compose](https://docs.docker.com/compose/how-tos/networking/).

## 3. Запуск на Windows

Откройте PowerShell в корне VIIO. Путь ниже замените на свой:

```powershell
Set-Location 'D:\Source\VIIO'
docker version
docker compose version
if (-not (Test-Path -LiteralPath '.env')) { Copy-Item -LiteralPath '.env.example' -Destination '.env' }
notepad .env
```

Сохраните настройки моделей и параметры из следующего раздела, закройте редактор и выполните:

```powershell
docker compose config --quiet
docker compose up -d --build
docker compose ps
Invoke-RestMethod http://localhost:3000/health
Invoke-RestMethod http://localhost:8000/health
```

## 4. Запуск на Linux

Откройте Bash в корне VIIO. Путь ниже замените на свой:

```bash
cd ~/VIIO
docker version
docker compose version
if [ ! -f .env ]; then cp .env.example .env; fi
nano .env
```

Сохраните настройки моделей и параметры из следующего раздела, затем выполните:

```bash
docker compose config --quiet
docker compose up -d --build
docker compose ps
curl --fail http://localhost:3000/health
curl --fail http://localhost:8000/health
```

### Параметры `.env` для обеих систем

Перед первым запуском задайте собственные `POSTGRES_PASSWORD` и `INTERNAL_API_KEY`. Для автоматического создания первого администратора также заполните `BOOTSTRAP_ADMIN_USERNAME` и `BOOTSTRAP_ADMIN_PASSWORD` (порядок ниже). Токен Compose передаёт обоим приложениям автоматически. Не публикуйте `.env`.

В текущем Compose пароль PostgreSQL подставляется также в URL подключения WebChat. Используйте длинный пароль из букв и цифр, чтобы специальные символы не нарушили URL.

| Переменная | По умолчанию | Назначение |
| --- | --- | --- |
| `POSTGRES_USER` | `postgres` | Пользователь PostgreSQL, не пользователь веб-чата |
| `POSTGRES_PORT` | `5432` | Порт PostgreSQL на хосте |
| `WEBCHAT_PORT` | `3000` | Порт веб-интерфейса |
| `API_PORT` | `8000` | Порт assistent |
| `QDRANT_PORT` | `6333` | HTTP-порт Qdrant |
| `QDRANT_GRPC_PORT` | `6334` | gRPC-порт Qdrant |
| `QDRANT_COLLECTION_NAME` | `knowledge_base` | Коллекция документов |

Если порт занят, измените соответствующую переменную и используйте новый порт в адресах ниже. Существующий `.env` команды копирования не перезаписывают.

### Как понять, что запуск завершён

В `docker compose ps` должны работать `postgres`, `qdrant`, `assistent`, `documents`, `document-worker`, `consultant` и `webchat`. Дождитесь прохождения проверок здоровья. Консультант отвечает только при включённом `CONSULTANT_ENABLED`.

Основной агент переименован в `Assistent`. Документы обслуживаются отдельно: API на порту 8002 и worker в отдельном контейнере. Веб-чат отправляет загрузки напрямую в Documents API. [Границы сервисов и запуск без Docker на Windows/Linux](../Documents/README.md).

- Откройте [веб-чат](http://localhost:3000).
- `/health` WebChat должен вернуть `db: true`.
- `/health` assistent должен вернуть `status: healthy`.
- [Документация API](http://localhost:8000/docs) показывает схемы запросов.

Проверка здоровья не подтверждает успешную генерацию ответа моделью: после регистрации отправьте короткий вопрос. Для проверки индексации загрузите небольшой документ по инструкции ниже.

### Настройки генерации моделей

Имена моделей задаются в `LMSTUDIO_MODEL` / `OLLAMA_MODEL`, модели эмбеддингов — в соответствующих переменных `*_EMBEDDING_MODEL`, отдельного coder — в `CODING_MODEL`.

| Параметр | По умолчанию | Назначение |
| --- | --- | --- |
| `CHAT_TEMPERATURE` | `0.0` | Температура консультанта, от 0 до 2 |
| `CHAT_TOP_P` | `1.0` | Порог выборки консультанта, больше 0 и до 1 |
| `CHAT_MAX_TOKENS` | `2048` | Максимум токенов ответа консультанта |
| `CODING_TEMPERATURE` | `0.0` | Температура coder, от 0 до 2 |
| `CODING_TOP_P` | `1.0` | Порог выборки coder, больше 0 и до 1 |
| `CODING_MAX_TOKENS` | `4096` | Максимум токенов ответа coder |

Лимиты ответа принимают значения от 128 до 32768. Это предел генерации, а не размер входной истории. При обрыве длинного кода увеличьте `CODING_MAX_TOKENS` с учётом возможностей сервера и лимита времени запроса. В Ollama лимит передаётся как `num_predict`, в LM Studio — как `max_tokens`.

Даже если `CODING_MODEL` пуст и имя модели совпадает с консультантом, настройки генерации coder применяются отдельно. Начальные параметры не гарантируют наилучшее качество: сравнивайте варианты на одинаковых задачах. Для применения изменений выполните `docker compose up -d assistent`.

Короткие системные инструкции находятся в `Assistent/src/assistent/prompts.py`: отдельно консультант, coder и делегирование. После их изменения требуется пересборка assistent.

## 5. Создать пользователя

1. Откройте веб-чат и выберите вкладку **«Регистрация»**.
2. Введите уникальный логин длиной от 3 до 64 символов и пароль не короче 6 символов.
3. Нажмите **«Создать учётную запись»**. Система создаст пользователя и выполнит вход.

Новый пользователь получает роль `employee` («Сотрудник») и подразделение `general`. Публичная регистрация не выдаёт административные права, даже первому пользователю. Первый администратор создаётся отдельно из настроек запуска; готового пароля в проекте нет.

### Назначить первого администратора

Рекомендуемый способ — задать в корневом `.env` перед запуском:

```dotenv
BOOTSTRAP_ADMIN_USERNAME=admin
BOOTSTRAP_ADMIN_PASSWORD=
```

Впишите собственный пароль в пустое значение: не короче 12 символов и не длиннее 72 байт UTF-8. Оба параметра должны быть заполнены вместе. В примерах по умолчанию оба пусты, создание выключено. Не регистрируйте этот логин через публичную форму заранее.

Примените настройки:

```text
docker compose up -d --build webchat
```

После запуска войдите по заданным логину и паролю на вкладке «Вход». Регистрировать этого пользователя не нужно.

- Если администраторов ещё нет, WebChat создаст одного с ролью `admin` и подразделением `general`.
- Если администратор уже есть, новая запись не создаётся, существующие пароль и права не меняются. Это не механизм сброса пароля.
- Если выбранный логин уже занят обычным пользователем, запуск с этими настройками завершится ошибкой. Выберите новый логин или назначьте права вручную.
- Если указан только один параметр или пароль не проходит проверку, WebChat сообщит об ошибке конфигурации. Если оба пусты, работает обычная регистрация без создания администратора.

После создания можно очистить оба значения и пересоздать WebChat: учётная запись сохранится. Для уже существующей установки с администратором настройка не требуется.

#### Ручное назначение существующему пользователю

Если требуется назначить администратором уже зарегистрированный логин, оператор установки может открыть psql из корня проекта:

```text
docker compose exec postgres psql -U postgres -d user_db
```

При изменённом `POSTGRES_USER` замените `postgres` после `-U`. Подставьте точный логин вместо `admin`:

```sql
SELECT id, username, role FROM users WHERE username = 'admin';
UPDATE users SET role = 'admin' WHERE username = 'admin'
RETURNING id, username, role;
```

Проверьте возвращённую запись, выйдите командой `\q` и обновите страницу веб-чата. Пароль при назначении роли не меняется.

### Назначить роль и подразделения

1. Войдите администратором и откройте **«Администрирование» → «Пользователи»**.
2. Найдите зарегистрированного пользователя и откройте редактирование его доступа.
3. Выберите роль, укажите подразделения через запятую, сохраните изменения.
4. Пользователю следует обновить страницу, чтобы интерфейс отразил новые права.

| Роль | Возможности |
| --- | --- |
| Сотрудник (`employee`) | Чат и документы, доступные по роли, подразделению или авторству |
| Руководитель (`manager`) | Чат и документы в соответствии с его правами |
| Программист (`programmer`) | Доступ к coder и документам сотрудников, а также к материалам своего подразделения |
| Администратор (`admin`) | Доступ к coder, управление доступом, загрузка документов и чтение всей базы знаний |

У пользователя одна роль. Coder доступен и администратору, и программисту; отдельная учётная запись для администратора не требуется. Последнего администратора нельзя понизить через интерфейс. Новые учётные записи создаются регистрацией; административный раздел изменяет права уже созданных пользователей.

## 6. Загрузить файлы в базу знаний

Загрузка доступна администратору:

1. Откройте **«Администрирование» → «База знаний»**.
2. Нажмите **«Выбрать файл»** и выберите `.pdf`, `.txt`, `.md` или `.markdown`. Для текстовых файлов используйте UTF-8. Либо вставьте текст вручную в поле **«Содержание»**.
3. Проверьте **«Название»** и прочитанный текст. Название ограничено 255 символами.
4. Выберите, кому доступен документ:

   | Вариант | Кто сможет найти документ |
   | --- | --- |
   | Сотрудникам | Сотрудники, руководители и программисты |
   | Подразделениям | Пользователи указанных отделов; имена вводятся через запятую, как в профилях |
   | Администраторам | Администраторы; автор документа также сохраняет доступ |
   | Всем | Все, включая гостевой контекст поиска |

5. Нажмите **«Добавить в базу знаний»** и дождитесь сообщения об успешной загрузке с числом созданных фрагментов.
6. Откройте чат пользователем с подходящими правами и задайте вопрос по содержимому. Например: «Что сказано в документе „Регламент отпусков“ о согласовании дат?»

Выбор файла только заполняет форму: индексация начинается после нажатия кнопки добавления. PDF ограничен **10 МБ и 50 страницами**, TXT/Markdown — **2 МБ**, текст — **500 000 символов**. Большие документы разделите на части с понятными названиями.

Текстовые PDF, DOCX и ODT разбираются на CPU в отдельном worker. Для сканов PDF запустите Docling: `docker compose --profile pdf up -d --build pdf-worker`. Подробности: [загрузка PDF](pdf-upload.md). Массовая загрузка принимает PDF/DOCX/ODT/TXT/Markdown и поддерживаемые исходники. DOCX/ODT индексируются автоматически после извлечения и очистки; PDF требует проверки распознанного текста. Оригиналы сохраняются без изменений, в Qdrant — поисковые фрагменты. [Правила очистки и ограничения Office](office-documents-2026-10-28.md).

Администратор и автор сохраняют доступ независимо от выбранного ограничения. В API права роли и подразделения объединяются по ИЛИ. В интерфейсе выбирается один вариант доступа.

В административном каталоге доступны карточки, скачивание оригиналов, история версий и загрузка новой версии выбранного документа. Публикация для внешнего консультанта выполняется отдельно. Удаление и политика хранения требуют отдельной настройки; совпадение названия не означает замену документа.

### Использовать документы при написании кода

Войдите пользователем с ролью «Программист» или «Администратор» и отправьте, например:

```text
/code По документу «Описание API заказов» напиши Python-клиент метода создания заказа.
```

Сервис подготовит сведения из доступной этому пользователю базы знаний и передаст их coder. Coder отвечает кодом в чат, не создаёт файлы и не запускает команды. Для надёжного продолжения задачи также начинайте уточнения с `/code`.

## 7. Остановка и повторный запуск

Дополнительно можно подключить тестовую PostgreSQL: заполните `PGSQL_*` в `.env` и запустите профиль `postgres`. Команды `/db`, требования к правам и ограничения описаны в [инструкции PostgreSQL](postgresql-tool.md). Доступ разрешён программистам и администраторам; по умолчанию инструмент выключен.

Команды одинаковы на Windows и Linux и выполняются из корня проекта:

```text
docker compose logs --tail 100 assistent webchat
docker compose down
docker compose up -d
```

Обычный `down` сохраняет именованные тома с пользователями, историей и знаниями. Не добавляйте `-v`, если эти данные нужны. После изменения `.env` примените настройки командой `docker compose up -d`; после обновления исходников — `docker compose up -d --build`.

## 8. Если что-то не работает

| Симптом | Что проверить |
| --- | --- |
| Docker недоступен | Запущен ли Docker Desktop / демон Docker, есть ли у пользователя права; работают ли `docker version` и `docker compose version` |
| Порт занят | Измените внешний порт в корневом `.env` и повторите `docker compose up -d` |
| Ошибка связи с моделью | Запущен ли сервер, совпадают ли имена моделей, доступен ли порт из контейнера; на Linux проверьте адрес прослушивания и firewall |
| `db: false` или ошибка регистрации | Состояние и логи `postgres` и `webchat`; подключение к `user_db` |
| Нет баз `user_db` / `agent_db` | Скрипт `init-db/init-databases.sh` выполняется только при первом запуске с пустым томом; для существующего тома нужна отдельная инициализация без удаления нужных данных |
| Скрипт инициализации выдаёт ошибку `\r` | Сохраните `init-db/init-databases.sh` с окончаниями строк LF; затем проверьте логи и состояние созданных баз |
| Сменили пароль БД в `.env`, подключение сломалось | Переменные образа PostgreSQL инициализируют пустой том; изменение `.env` не меняет пароль существующей роли в БД |
| Нет «Администрирования» | Проверьте назначенную роль `admin` и обновите страницу |
| Coder отказывает в доступе | Нужна роль `programmer` или `admin`, включённая в `CODING_ALLOWED_ROLES`; сотрудникам и руководителям доступ закрыт |
| Документ не находится | Проверьте успешную индексацию, название, роль и подразделения текущего пользователя; задайте конкретный вопрос по тексту |
| После смены модели эмбеддингов ошибка размерности | Существующая коллекция рассчитана на прежнюю модель; для новой модели используйте отдельную коллекцию и повторную загрузку документов |
| Вход не сохраняется при доступе по IP через HTTP | Production-сборка использует Secure-cookie. Для удалённого доступа настройте HTTPS; локальный сценарий инструкции использует `localhost` |

`INTERNAL_API_KEY` предназначен для серверного обмена, не для входа пользователей. Запросы напрямую в assistent к `/api/v1/chat` и `/api/v1/documents` требуют заголовка `X-Internal-Token`. Для обычной работы используйте веб-интерфейс.

Дополнительно: [настройка coder](mcp-integrations.md), [WebChat](../WebChat/README.md), [assistent](../Assistent/README.md).
