# PostgreSQL: инструмент чтения тестовой базы

VIIO использует готовый [Postgres MCP Pro](https://github.com/crystaldba/postgres-mcp) через официальный Python MCP SDK. Сервер работает отдельным контейнером с фиксированным `--access-mode=restricted`; образ закреплён по digest в корневом Compose. Его Python-зависимости не устанавливаются в APIAgent.

Доступ разрешён только пользователям с ролью **Программист (`programmer`)** или **Администратор (`admin`)**. Сотрудники, руководители и гости не допускаются. Проверки выполняются перед вызовом инструмента APIAgent; WebChat дополнительно проверяет команды `/db`. Coder по-прежнему пишет код без инструментов; обращения к БД выполняет отдельный серверный помощник через `/db` или естественный вопрос о подключённой БД, например: «Какие таблицы есть в подключённой тестовой PostgreSQL?».

Для естественного вопроса помощник использует основную модель, которая выбирает операцию `postgresql_readonly`. Роль и включение интеграции проверяются до модели. При `PGSQL_ENABLED=false` возвращается сообщение об отключении, без поиска документов и подключения к БД. Результаты БД не сохраняются в checkpoints диалога. Вопросы о теории PostgreSQL и написании самостоятельного SQL-примера остаются в обычном маршруте.

## Настройка подключения

В корневом `.env` заполните параметры своей тестовой PostgreSQL:

```dotenv
PGSQL_ENABLED=true
PGSQL_HOST=host.docker.internal
PGSQL_PORT=5432
PGSQL_DATABASE=test_db
PGSQL_USER=viio_reader
PGSQL_PASSWORD=
PGSQL_SSLMODE=prefer
PGSQL_MCP_URL=http://postgres-tool:8000/sse
PGSQL_MAX_ROWS=100
PGSQL_MAX_CHARS=12000
PGSQL_TIMEOUT_SECONDS=40
```

Впишите собственный пароль в `PGSQL_PASSWORD`, если сервер требует пароль. Логин и пароль могут оставаться пустыми только при соответствующей настройке аутентификации самого PostgreSQL. Это не учётные данные веб-чата.

`PGSQL_HOST` — IP или имя сервера БД, без `http://` и `/v1`. Для PostgreSQL на том же компьютере используйте `host.docker.internal`, для другого сервера — его сетевой адрес. `PGSQL_PORT` — порт PostgreSQL, а не HTTP API. Пароли со знаками `$` в Compose `.env` заключайте в одинарные кавычки.

`PGSQL_SSLMODE` допускает режимы libpq; для удалённого сервера настройте TLS по требованиям вашей инфраструктуры. Пароль передаётся только контейнеру MCP-сервера через окружение и не включается в аргументы запуска или сообщения модели. Не используйте здесь доступ к служебным базам VIIO вместо тестовой БД.

По умолчанию инструмент выключен, параметры БД и учётные данные пусты. Тестовая БД автоматически не создаётся.

## Пользователь БД

Используйте отдельный PostgreSQL-логин с правом SELECT только на нужные таблицы, без superuser, владения объектами и прав изменения. Ограниченный режим MCP дополняет права PostgreSQL, а не заменяет их.

Пример для администратора **тестовой БД**, выполняемый в psql после выбора нужной базы:

```sql
CREATE ROLE viio_reader LOGIN;
\password viio_reader
GRANT CONNECT ON DATABASE test_db TO viio_reader;
GRANT USAGE ON SCHEMA public TO viio_reader;
GRANT SELECT ON TABLE public.orders TO viio_reader;
```

Подставьте реальные имена тестовой базы и разрешённых таблиц. Не выдавайте права записи или доступ ко всем данным без необходимости. Команда `\password` интерактивно задаёт пароль, не сохраняя его в тексте SQL-примера. Для новых таблиц права выдаются отдельно.

## Запуск

Из корня VIIO, одинаково в PowerShell и Bash:

```text
docker compose --profile postgres config --quiet
docker compose --profile postgres up -d --build postgres-tool apiagent webchat
docker compose --profile postgres ps
```

Профиль `postgres` добавляет готовый MCP-сервер. Его HTTP-порт не публикуется на хост и доступен внутри сети Compose. Секреты изменяются через `.env`; после изменения выполните `docker compose --profile postgres up -d postgres-tool apiagent`.

В каталоге `APIAgent` самостоятельный Compose не запускает дополнительный сервер: при таком сценарии укажите доступный внешний `PGSQL_MCP_URL` либо используйте корневой Compose.

## Использование

Войдите программистом или администратором и отправьте:

```text
/db schemas
/db tables public
/db describe public.orders
/db SELECT id, total FROM public.orders ORDER BY id
/db query SELECT count(*) AS total FROM public.orders
/db explain SELECT id FROM public.orders WHERE created_at >= DATE '2026-01-01'
```

Эти команды вызывают готовый инструмент непосредственно и не зависят от способности модели выбрать нужный tool call. `describe` принимает `schema.table` или имя таблицы из `public`. `explain` получает оценочный план SELECT без ANALYZE и без добавления LIMIT, чтобы лимит выдачи не менял план оптимизации. Выполнение запроса через EXPLAIN ANALYZE и создание гипотетических индексов отключены.

Можно задать вопрос словами:

```text
/db Сколько всего заказов в таблице public.orders? Проверь реальную БД.
```

Тогда консультант получает только инструменты чтения БД в отдельном графе без сохранения состояния. Короткие продолжения также начинайте с `/db` и повторяйте необходимый контекст. `/code` остаётся режимом написания кода и SQL-текста без исполнения.

## Ограничения и история

- Запись, изменение схемы и выход из ограниченной транзакции не предоставляются. Сервер запускается только в `restricted`-режиме, SQL обрабатывается готовым MCP-сервером.
- SELECT оборачивается внешним запросом с лимитом `PGSQL_MAX_ROWS` (от 1 до 500). Это ограничивает возвращённые строки; агрегаты вроде `count(*)` считают исходный набор.
- Текст результата ограничен `PGSQL_MAX_CHARS`. Время ожидания клиента задаётся `PGSQL_TIMEOUT_SECONDS`; общий запрос помощника ограничен 95 секундами.
- В БД чата вместо запросов `/db` и результатов сохраняются только нейтральные отметки. Результат виден в текущем ответе, но после перезагрузки страницы его нужно запросить заново. Это исключает повторную выдачу сохранённого результата после смены роли.
- В состояние обычного консультанта и coder результаты `/db` не передаются. Сами значения из БД рассматриваются как данные, а не инструкции.
- Качество ответа на естественном языке зависит от модели; при необходимости точного выполнения используйте явный SELECT. Имена и результат сверяйте с фактической схемой.

## Проверка реализации · 26.10.2026

Дополнительно проверена оптимизация на 100 000 искусственных строк: условие `date(created_at) = DATE '2020-03-01'` давало Seq Scan с оценкой стоимости до 2041; диапазон по `created_at` использовал существующий индекс и Index Scan со стоимостью до 8,77. Это оценки планировщика, а не измеренное ускорение. Попытка передать `pg_sleep(3)` отклонена ограниченным сервером. Автотесты запрещают ANALYZE и гипотетические индексы.

На отдельной временной PostgreSQL 16 с таблицей из двух искусственных заказов и пользователем SELECT проверены схемы, список таблиц, описание и выборка. Лимит 3 строки проверен на наборе из 10 строк. Отклонены INSERT, DELETE внутри CTE, DROP и попытка выйти через ROLLBACK. После проверок исходные две строки сохранены. Запрос через локальную модель вернул правильный ответ о двух заказах.

Автоматические тесты проверяют роли, отсутствие вызова БД при отказе, отключённую конфигурацию, маскирование ошибок и отсутствие SQL/результатов в истории WebChat. Проверка тестовой базы не означает подключения к вашей БД: её реквизиты нужно заполнить отдельно.

Текущая общая проверка: 116 тестов APIAgent и 32 теста WebChat прошли, сборка успешна. Архитектурный анализ не выявил циклов, но отметил рост числа функций повышенной сложности с 10 до 11 после расширения системы. Временные контейнеры и искусственная БД удалены после проверки. Основные сервисы обновлены; рабочий `.env` оставлен с `PGSQL_ENABLED=false` и пустыми реквизитами БД.
