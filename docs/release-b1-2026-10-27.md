# Каталог и массовая загрузка: первый рабочий этап

Дата проверки: 27 октября 2026. Исходная точка Git: `4f3a1b6`.

Последующее изменение: [проверка PDF и отмена загрузок](release-b2-review-2026-10-27.md). Описанное ниже автоматическое индексирование PDF заменено обязательной проверкой администратором.

Это часть этапов 3–4 общего плана. История версий, изменение прав с переиндексацией, удаление, проверка OCR и публикация для внешнего консультанта ещё не завершены.

## Проверка работы предыдущей модели

Код проверен по двум направлениям: работоспособность и соответствие плану.

### Работоспособность

В первоначальном черновике обнаружены ошибки, блокирующие загрузку:

- Каталог оставался без подключения, если PostgreSQL-checkpointer успешно запускался.
- SQL использовал `$1` вместо параметров `%s`, поддерживаемых psycopg; чтение счётчика не соответствовало `dict_row`.
- Вызов фонового потока передавал именованные аргументы непосредственно в `run_sync`.
- Русский заголовок файла вызывал ошибку кодировки HTTP-заголовка.
- Синхронная индексация пыталась зарегистрировать каталог через отсутствующий event loop рабочего потока. Ошибки регистрации подавлялись.

Исправления проверены на PostgreSQL, а не только на моках. Файлы SQL-каталога, обработки и очереди разделены; недоступный каталог не выдаётся за успешную загрузку.

### Соответствие плану

Первоначальная очередь держала байты и результаты в памяти. Она заменена в приложении на журнал `document_upload_jobs` в PostgreSQL и постоянное файловое хранилище. Получение задания атомарно через `FOR UPDATE SKIP LOCKED`; право обработки имеет срок действия и продлевается. После перезапуска ожидающее или просроченное задание может быть продолжено. Обычная остановка возвращает незавершённое задание в очередь.

Дедупликация учитывает владельца, содержимое и права. Конкурентная обработка одного документа сериализуется PostgreSQL advisory lock. Повтор использует одинаковые идентификаторы поисковых записей. Незавершённые записи скрыты от поиска; готовность выставляется после сохранения каталога.

Скачивание учитывает роль, наследование programmer → employee, отдел и владельца. Контекст берётся веб-сервером из сессии; параметры браузера не позволяют подменить его. Это сохраняет действующую политику поиска: достаточно одного разрешающего условия, администратор имеет полный доступ.

## Что доступно

- Каталог документов с постраничным просмотром и отметкой наличия оригинала.
- Загрузка нескольких PDF/TXT/Markdown с общими правами.
- Независимые статусы, повтор ошибочного задания, просмотр последних 100 заданий после повторного открытия страницы.
- Сохранение оригинальных байтов массово загруженного файла в Docker-томе `documents_storage`.
- Добавление отредактированного текста через прежнюю форму с сохранением его как TXT.
- Миграция метаданных существующего индекса в каталог при запуске. Оригиналы старых документов не восстанавливаются из поисковых фрагментов.

## Как пользоваться

1. Войти администратором, открыть «База знаний» → «Массовая загрузка».
2. Выбрать файлы и общие права доступа. По умолчанию допускаются до 50 файлов, до 10 МБ каждый. Веб-сервер ограничивает весь multipart-запрос 50 МБ с учётом его служебной части.
3. Отправить файлы и дождаться индивидуальных результатов. При ошибке доступна кнопка «Повторить обработку». Неподдерживаемый файл, отклонённый до сохранения задания, нужно выбрать заново.
4. Во вкладке «Каталог» скачать сохранённый оригинал. Старые записи без оригинала такой возможности не имеют.

Для Windows и Linux с Docker команды одинаковы, выполнять из корня проекта:

```text
docker compose build apiagent webchat
docker compose up -d
docker compose ps
```

Конфигурация: `DOCUMENTS_CATALOG_ENABLED`, `DOCUMENTS_STORAGE_PATH`, `BULK_MAX_FILES`, `BULK_MAX_FILE_BYTES`, `BULK_MAX_WORKERS`. В Docker путь оригиналов — `/data/documents`. При запуске Python без Docker значение по умолчанию — `data/documents` относительно рабочего каталога; папка исключена из Git.

Нужно сохранять и PostgreSQL, и файловый том. Одного дампа базы недостаточно для восстановления оригиналов. Тест восстановления дампа `agent_db` выполнен в отдельной временной базе; проверены четыре таблицы сохранения диалогов. Это не проверка восстановления всех томов системы.

## Проверки

- 186 проверок API, включая шесть интеграционных сценариев на настоящей PostgreSQL с отдельной временной схемой для каждого теста.
- Партия из 50 файлов: 49 текстовых/Markdown обработаны, повреждённый PDF получил отдельную ошибку. Векторы в этом сценарии используют локальные тестовые embeddings; это функциональная проверка, не замер производительности модели.
- Проверены повтор после ошибки, восстановление просроченного задания, остановка рабочего процесса, конкурентная дедупликация, отказ каталога и скрытие незавершённого индекса.
- 38 проверок веб-сервера, включая защиту от подмены прав при скачивании и ограничение повтора загрузки администратором.
- Сборка TypeScript и Vite.
- Живая система с настроенными embeddings/Qdrant: TXT, Markdown и PDF успешно обработаны; повреждённый PDF не остановил остальные; EXE отклонён. После настоящего перезапуска APIAgent проверены исходные байты и запрет скачивания сотрудником. Тестовые документы затем удалены по идентификаторам этого прогона.

Интеграционные тесты включаются переменной `VIIO_TEST_PG_DSN`, указывающей на тестовую PostgreSQL. Каждый тест создаёт и удаляет только собственную случайно названную схему. Пример команды из каталога `APIAgent` после настройки переменной:

```text
uv run pytest tests/test_document_pipeline_integration.py -q
```

Сценарий живой проверки находится в `APIAgent/scripts/check_document_upload.py`: режимы `begin`, `verify`, `cleanup`; между первыми двумя перезапускают APIAgent. Запускать внутри настроенного контейнера. Его служебный файл `/tmp/viio-upload-check.json` должен сохраняться между режимами: `docker compose restart` его сохраняет, пересоздание контейнера — нет.

## Следующая часть плана

1. Проверка распознанного текста перед публикацией, отмена задания, лимиты общей очереди и объёма хранения.
2. История версий, активная версия индекса, согласованное удаление и отзыв доступа. Поля `version` и `parent_id` в схеме сами по себе не означают готовую функцию версий.
3. Привязка повторно загруженного оригинала к старому документу после проверки соответствия.
4. Отдельное состояние публикации и набор разрешённых материалов для внешнего консультанта. Текущий `is_public` внутренней базы нельзя автоматически считать разрешением внешней публикации.

Массовый импорт пока индексирует распознанный PDF автоматически. Для сканов, требующих проверки человеком, использовать одиночную форму извлечения и редактирования текста. В ней сохраняется утверждённый TXT, а не исходный PDF. Производственные нагрузочные измерения Docling CPU и визуальная проверка нового интерфейса в браузере в этот прогон не входят.
