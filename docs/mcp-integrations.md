# Готовые MCP-серверы VIIO

Основной агент напрямую использует доступные текущему пользователю инструменты.
Отдельных coder и DB-агента в приложении нет. Поиск по БЗ доступен с текущими
правами на документы; GitHub и PostgreSQL передаются модели только для
авторизованных программистов и администраторов при включённой интеграции.
Проверка роли повторяется при выполнении инструмента. При смене роли прежняя
история с другой областью доступа не передаётся модели.

## План, потоковый ответ и сохранение знаний

Для составных запросов агент использует `manage_plan`: создаёт короткий список
действий, выполняет их и обновляет статусы. Для простого вопроса план не нужен.
`AGENT_MAX_TOOL_CALLS` задаёт общий бюджет инструментов на запрос (по умолчанию 24).
План описывает действия и результаты, без скрытых рассуждений модели.

Сайт отправляет `/api/chat` с `stream=true`, WebChat обращается к
`/api/v1/chat/stream`. SSE-события: `status`, `plan`, `reset`, `delta`, `done`, `error`.
Фрагменты текста появляются во время генерации; при смене вызова модели
временный текст заменяется. Итоговое `done` отправляется после сохранения ответа
в истории. Незавершённые фрагменты в БД не сохраняются. Права на знания
перепроверяются перед выдачей фрагментов и после выполнения запроса.

`save_knowledge` доступен только авторизованному администратору при настроенном
`DOCUMENTS_ADMIN_KEY` у Assistent. Пример: «Сохрани в общую базу знаний:
заголовок — Порядок обработки заявки; текст — …».
В инструмент передаются только заголовок (до 255 символов) и текст
(до 20000 символов). Автор берётся из серверного контекста, права фиксированы:
employee, manager, programmer, admin, без внешней публикации.
Documents сохраняет оригинал и каталог, worker создаёт эмбеддинги и индекс Qdrant.
Успех подтверждается только после индексации. При таймауте проверьте каталог:
запись могла завершиться, даже если ответ не получен. Прямого доступа агента
к записи в Qdrant нет; используется обычный конвейер документов.

## GitHub

Используется официальный удалённый GitHub MCP Server:
https://github.com/github/github-mcp-server/blob/main/docs/remote-server.md

Адрес: `https://api.githubcopilot.com/mcp/readonly`, транспорт Streamable HTTP.
Локальный Git-сервер не нужен. В `.env` задайте:

```dotenv
GITHUB_MCP_ENABLED=true
GITHUB_MCP_TOKEN=<fine-grained personal access token>
GITHUB_REPOSITORY=<owner>/HandbookBot2
```

Соединениями GitHub и PostgreSQL управляет готовый `langchain.mcp.MCPAdapter`.
Список репозиториев (`operation=repositories`, `page` от 1) получается через
GitHub REST `GET /user/repos`; при фиксированной области — `GET /repos/owner/repo`.
Если hosted GitHub MCP ошибочно отклоняет обычный файл с сообщением
`not a valid internal symbolic link target`, адаптер читает тот же путь и ref
через GitHub REST Contents API с тем же токеном. Внешние ссылки и подмодули
не загружаются; остальные ошибки MCP не включают этот обход.
Обёртки VIIO оставляют доступ только к разрешённым операциям и проверяют роли.
Подробности внедрения и миграция памяти: `docs/ready-agent-components.md`.

Создайте токен с доступом к нужным репозиториям и разрешением Contents:
read-only. При необходимости организация должна одобрить токен. Не отправляйте
токен в чат и не коммитьте `.env`.

Код HandbookBot2 должен находиться в указанном GitHub-репозитории: локальный
путь `C:/Users/kanl2/source/repos/HandbookBot2` удалённому MCP не виден.
Доступен опубликованный код, включая выбранную ветку; локальные изменения
нужно отдельно закоммитить и отправить обычным Git.

Адаптер `github_repository` вызывает готовые инструменты `get_file_contents`,
`search_code`, `list_commits`, `get_commit`, `list_branches`. Репозиторий выбирается
оператором в настройках. `GITHUB_REPOSITORY=*` разрешает все репозитории,
доступные токену: для файлов, веток и истории агент передаёт `repository=owner/repo`,
для поиска может опустить repository и искать по всем доступным репозиториям.
В настройках fine-grained токена выберите All repositories для выбранного владельца
и Contents: Read-only. Ограничения токена сохраняются; настройка * их не расширяет.
Все разрешённые пользователи имеют общий доступ в рамках серверного токена.
Поиск принимает обычные слова без квалификаторов. Поиск и списки
ограничены первыми 20 результатами; большие результаты сокращаются до
GITHUB_MCP_MAX_CHARS (16000). Инструмент доступен только разрешённым в
CODING_ALLOWED_ROLES программистам и администраторам.

```text
Какие репозитории тебе доступны?
Покажи корневые файлы GitHub-репозитория owner/HandbookBot2.
Найди обработчики сообщений в GitHub и объясни их работу.
```

## PostgreSQL

В проект уже интегрирован готовый Postgres MCP Pro
(https://github.com/crystaldba/postgres-mcp). Сервис `postgres-tool` запускается
в restricted-режиме и проверяет, что роль базы имеет только права чтения.
Инструмент `postgresql_readonly` позволяет получать схемы, таблицы, столбцы,
выполнять SELECT и EXPLAIN без ANALYZE. Он передаётся основному агенту с учётом роли.

Настройте существующие переменные `.env`:

```dotenv
PGSQL_ENABLED=true
PGSQL_HOST=<database-host>
PGSQL_PORT=5432
PGSQL_DATABASE=<database-name>
PGSQL_USER=<read-only-user>
PGSQL_PASSWORD=<password>
PGSQL_MCP_URL=http://postgres-tool:8000/sse
```

Не используйте учётную запись владельца базы или суперпользователя.
Для БД на компьютере с Docker Desktop используйте host.docker.internal
в PGSQL_HOST. Этот сервер поддерживает PostgreSQL; для SQL Server, MySQL
или SQLite потребуется другой готовый MCP.

```text
Покажи схемы подключённой PostgreSQL.
Покажи таблицы схемы public и структуру public.orders.
Посчитай количество строк в public.orders.
```

## Запуск

```powershell
docker compose --profile postgres up -d --build postgres-tool assistent
```

Для одного GitHub:

```powershell
docker compose up -d --build assistent
```

Оба подключения выключены по умолчанию. Реальные токен GitHub и параметры БД
оператор задаёт отдельно. Данные репозитория и результаты БД обрабатывает общая
модель `CHAT_PROVIDER` / `CHAT_MODEL` с наследованием `LLM_PROVIDER`.
Для Yandex контекст и результаты инструментов отправляются в облако.
Параметры `CODING_*` (кроме ролей GitHub) и `DATABASE_PROVIDER` / `DATABASE_MODEL`
сохранены для совместимости, но отдельные модели в приложении не создают.
