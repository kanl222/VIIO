# Поиск, код организации, память и внешний API

27 октября 2026. Первый совместный выпуск по направлениям 5, 6, 8 и 10 плана.

## Поиск и исходники

Внутренний поиск параллельно получает семантические результаты Qdrant и полнотекстовые кандидаты PostgreSQL. Заголовки, имена файлов, идентификаторы и совпадения в тексте влияют на порядок; перед повторными фрагментами одного документа показываются разные документы. Дополнительная модель для ранжирования не вызывается. Если один механизм недоступен, используется второй; если недоступны оба — возвращается ошибка поиска.

Текстовое представление хранится отдельно в `document_contents`, с GIN-индексом русского текста и идентификаторов. При запуске для прежних документов оно собирается из существующих поисковых фрагментов. Это поисковое представление, а не восстановленный оригинал. Старые оригиналы не появляются автоматически. Для новых документов сохраняется утверждённый текст. Архивные версии исключены из обоих механизмов поиска.

Администратор может массово загрузить исходные файлы Python, JS/TS/JSX/TSX, SQL, Go, Java, C/C++/C#, Ruby, PHP, Rust, YAML/JSON/TOML, shell/PowerShell, XML/WSDL. Исходники не запускаются и не записываются обратно в проект. Доступ всегда ограничивается программистами и администраторами, независимо от общих прав партии; ограничение действует и на скачивание владельцем, утратившим эту роль.

У исходников сохраняются имя файла и номера строк. Python разбивается с учётом верхнеуровневых функций и классов, крупные блоки и другие языки — по ограниченным блокам строк. Coder получает найденные фрагменты как справку и продолжает отвечать кодом в чат без инструментов.

Автоматический обход Git-репозиториев, ветки/коммиты и полноценный синтаксический анализ остальных языков пока не реализованы. Качество ранжирования нужно оценивать на вопросах организации; текущие проверки не доказывают улучшение всех ответов или ускорение каждого запроса.

## Сводки и сохранённые факты

Длинная беседа сжимается в сводку цели, решений и открытых вопросов. Полный журнал остаётся в checkpoint PostgreSQL; модель получает сводку и последние сообщения. Сводка сохраняется вместе с графом, обновляется порциями, а не на каждом запросе. Она не превращается автоматически в подтверждённые факты. Результаты инструментов не передаются в запрос суммаризатора. При смене пользователя, роли или отдела прежняя сводка исключается из контекста.

Настройки: `CONVERSATION_SUMMARY_ENABLED=true`, `CONVERSATION_SUMMARY_AFTER=24`, `CONVERSATION_HISTORY_MAX_CHARS=18000`. Суммаризация использует настроенную чат-модель без инструментов и добавляет отдельный вызов модели при достижении порога. При ошибке используется ограниченное окно сообщений. Эта функция ограничивает контекст модели, а не размер базы полного журнала.

Постоянные пользовательские заметки сохраняются только явно:

```text
/remember Для учебных примеров использовать Python 3.12
запомни Для учебных примеров использовать Python 3.12
/facts
/forget идентификатор_факта
```

Русские псевдонимы: `/факты`, `/забыть`. Записи содержат пользователя, контекст доступа, исходный диалог и дату. Дубли не добавляются; ограничение — 100 записей по 2000 символов. Пароли и типовые токены/ключи блокируются проверкой текста; это не полноценный классификатор всех возможных секретов, поэтому не следует сохранять в заметки секретные значения.

Факты доступны только своему пользователю в том же контексте роли и отделов. Можно удалить собственную запись по ID после смены роли, но нельзя прочитать прежний привилегированный набор или удалить чужую запись. В модель передаются до 20 последних заметок, суммарно до 4000 символов, как утверждения пользователя, а не проверенные сведения организации. Автоматического извлечения корпоративных фактов и общих фактов между пользователями пока нет.

## Внешний консультант: только API

По выбору пользователя адаптер мессенджера пока не добавляется. Новый маршрут:

```text
POST /api/v1/consultant/chat
X-Consultant-Key: отдельный_ключ
Content-Type: application/json

{"message":"Когда работает поддержка?"}
```

Ответ содержит `reply` и `sources` с публичными названиями и идентификаторами публикаций. Роль, отдел, внутренний thread ID и другие параметры пользователя не принимаются. Внешний API использует отдельную модель без инструментов, без истории внутренних диалогов, личных фактов, coder, PostgreSQL-инструмента и внутреннего семантического поиска.

Он читает только `document_publications`: отдельные тексты, явно проверенные и опубликованные администратором. Внутренний `is_public` сам по себе не даёт внешний доступ. Нет совпадений в опубликованных текстах — нет вызова модели и нет ответа по её общим знаниям. После генерации повторно проверяются идентификаторы публикаций: отозванный или заменённый материал не выдаётся завершившимся ответом.

В каталоге администратор выбирает **«Внешняя публикация»**, вводит публичное название и отдельный проверенный текст, затем нажимает **«Опубликовать для внешнего API»**. Внутреннее содержимое не копируется автоматически. Исходники публиковать нельзя. Кнопка **«Отозвать публикацию»** исключает текст из новых запросов. При активации новой версии документа прежняя публикация удаляется в той же транзакции PostgreSQL; новую нужно подтвердить отдельно.

Консультант не хранит внешний диалог между запросами. Его поиск пока полнотекстовый; семантический индекс только опубликованных материалов и адаптер мессенджера остаются следующими улучшениями. Одновременно обрабатываются не более двух внешних генераций в одном процессе, общий тайм-аут запроса — 60 секунд.

## Настройка Windows и Linux

В `.env`:

```text
CONSULTANT_ENABLED=true
CONSULTANT_API_KEY=отдельный_случайный_ключ_не_короче_32_символов
```

Не использовать `INTERNAL_API_KEY` для внешних клиентов. В текущем локальном окружении отдельный случайный ключ настроен в игнорируемом Git файле `.env`; значение не выводилось в отчёты и не попадает в веб-сборку.

Из корня проекта, после коммита проверенного выпуска:

```text
docker compose build apiagent webchat
docker compose up -d
docker compose ps
```

Для проверки из PowerShell:

```powershell
$headers = @{ 'X-Consultant-Key' = $env:CONSULTANT_API_KEY }
$body = @{ message = 'Когда работает поддержка?' } | ConvertTo-Json
Invoke-RestMethod -Method Post -Uri http://localhost:8000/api/v1/consultant/chat -Headers $headers -ContentType 'application/json; charset=utf-8' -Body ([Text.Encoding]::UTF8.GetBytes($body))
```

В Linux:

```bash
curl http://localhost:8000/api/v1/consultant/chat \
  -H "X-Consultant-Key: $CONSULTANT_API_KEY" -H 'Content-Type: application/json' \
  -d '{"message":"Когда работает поддержка?"}'
```

Переменная оболочки не загружается из `.env` автоматически: перед примером задать её локально, не публикуя значение ключа. До первой явной публикации консультант отвечает, что сведений недостаточно.

## Проверки перед выпуском

207 проверок API и 45 проверок веб-сервера прошли. Включены настоящая PostgreSQL в изолированных схемах, поиск по именам исходников и идентификаторам, доступ по ролям и отделам, сохранение и удаление своих фактов, изоляция контекста, сводки checkpoint, запрет публикации исходников, отдельный ключ, отказ от подставленной роли, отзыв публикации во время генерации и при смене версии.

Сборка TypeScript/Vite выполнена. Перед миграцией сохраняется дамп `agent_db`. Живой сценарий `APIAgent/scripts/check_knowledge_memory_consultant.py` проверяет использование исходника coder, ответ внешнего консультанта по синтетической публикации, отсутствие внутреннего маркера, суммаризацию настроенной моделью и сохранение сводки/фактов после перезапуска. Результат живого прогона фиксируется после обновления.

Не выполнены: визуальная проверка новых форм в локальном браузере и производственный нагрузочный тест. Отзыв прав внутренних документов, удаление семейств, лимиты хранения и автоматический импорт Git остаются в общем плане.
