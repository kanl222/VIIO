# Documents отдельно от Assistent; выпуск A

## Границы

`Documents/src/viio_documents` — самостоятельный Python-пакет с собственными `pyproject.toml`, `uv.lock`, Dockerfile, тестами и сценариями обслуживания. Образ собирается из каталога Documents, без копирования Assistent. В нём нет моделей диалога/coder и LangGraph. Assistent не импортирует Documents, не устанавливает Qdrant/Office/PDF-парсеры и не обслуживает операции документов. Его связь с базой знаний — HTTP-контракт Documents.

Старый прокси `/api/v1/documents/...` на Assistent удалён. Клиентам нужно использовать Documents API; WebChat уже обращается к нему напрямую. Пакет `viio_documents` заменяет старые импорты документных классов из `assistent`. Сценарии импорта и обслуживания перемещены в `Documents/scripts`. Тесты нескольких сервисов из checkout устанавливают пути исходников обоих пакетов; production-образы от этого не зависят.

Каталог/очередь/снимки остаются в существующей `agent_db`, оригиналы — в прежнем Docker-томе, коллекции — прежние. Переиндексация корпуса при разделении не нужна. После очистки инструкции в каталоге 79 записей версий, из них 75 активных, и 43 публикации.

## Полномочия и отзыв

| Ключ | Кто хранит | Разрешение |
|---|---|---|
| CHAT_API_KEY | WebChat, Assistent | Вызов чата |
| DOCUMENTS_READ_KEY | Assistent, WebChat, Documents API | Поиск, проверка ревизии доступа, скачивание с проверкой ACL |
| DOCUMENTS_ADMIN_KEY | WebChat, Documents API | Каталог, загрузка, версии, очередь, публикации |
| DOCUMENT_WORKER_KEY | Documents API, worker | Обработка/индексация в worker |
| CONSULTANT_SOURCE_KEY | Consultant, Documents API | Только разрешённые опубликованные снимки |
| CONSULTANT_API_KEY | Внешний клиент, Consultant | Внешний API консультанта |
| DOCLING_API_KEY | worker, PDF-worker | CPU OCR |
| QDRANT_READ_KEY | Documents API, Qdrant | Чтение индексов |
| QDRANT_API_KEY | worker, Qdrant | Изменение индексов |

В Compose включён `SECURE_RUNTIME=true`: обязательны разные ключи длиной минимум 32 символа; отсутствие ключей блокирует запуск. Общий шаблонный INTERNAL_API_KEY больше не передаётся приложениям. Внутренние запросы без подходящего ключа отклоняются до чтения тела файла. В локальных изолированных тестах остаётся явный legacy-параметр INTERNAL_API_KEY; это не production-режим.

Для ротации доступны CHAT_API_KEY_PREVIOUS, DOCUMENTS_READ_KEY_PREVIOUS, DOCUMENTS_ADMIN_KEY_PREVIOUS и DOCUMENT_WORKER_KEY_PREVIOUS. Сначала включите приём старого и нового ключа на соответствующем сервере, затем обновите клиентов, после проверки удалите PREVIOUS. Старый ключ чтения не приобретает права записи. Ротация не выполняется автоматически по таймеру.

Результаты поиска перепроверяются по актуальному каталогу: устаревший ACL в векторном payload не даёт доступ. Для старой версии при скачивании проверяется также ACL актуального документа семейства. Assistent получает непрозрачную ревизию прав до и после генерации; при изменении ревизии готовый ответ блокируется, а на следующем ходе старая история знаний/сводка не передаётся модели. Ревизия общая для каталога: пока это может сбрасывать контекст и при изменении несвязанного документа. Пользовательские факты имеют отдельную область доступа и от этой ревизии не зависят.

Consultant сохраняет независимую проверку UUID публикаций после генерации. Права пользователя берутся WebChat из серверной сессии, а не из присланного role/owner/departments. Ключи и доверенный контекст не выдаются браузеру.

## PostgreSQL и контейнеры

Сервисы используют отдельные NOSUPERUSER/NOCREATEDB/NOCREATEROLE роли. `viio_assistent` имеет DML только для checkpoints и user_facts; `viio_documents` читает каталог/содержимое/публикации и управляет очередью; `viio_worker` изменяет документные таблицы; `viio_webchat` работает только с пользовательскими таблицами user_db. Сервисам не выдаётся CREATE на схему. Миграции выполняются отдельно учётной записью развёртывания; runtime startup использует `DATABASE_MIGRATIONS_ENABLED=false`.

SQL MCP остаётся отдельным optional profile и запускается в restricted/read-only режиме с ограничением времени. Для подключения сторонней тестовой БД необходимо выдать PGSQL_USER отдельную роль без прав записи; права внешней базы не меняются автоматически миграцией VIIO. При выключенном profile она не подключается к базе.

Все прикладные контейнеры запускаются без root, с read-only root filesystem, сброшенными capabilities и no-new-privileges. Для временных данных выделен tmpfs; worker/API сохраняют оригиналы и задания в прежнем томе, Docling — модели в своём томе. До перехода на UID 65532 существующим файловым томам нужно предоставить соответствующее владение.

Основной Compose оставляет диагностические PostgreSQL/Qdrant/Assistent/Documents порты только на 127.0.0.1. Production override убирает их полностью. WebChat и Consultant остаются входными сервисами; размещение внешнего TLS/gateway настраивается окружением. Ключ Qdrant обязателен и для прямых запросов; API документов получает только readonly-вариант.

## Первый запуск: Windows и Linux

Команды выполняются из корня проекта. Нужны Docker Compose с поддержкой `!reset`, доступ к настроенному серверу моделей и Python 3.12+. Скопируйте `.env.example` в `.env`, задайте параметры моделей и администратора развёртывания PostgreSQL. Для существующей установки используйте прежний `.env` и тома.

Windows PowerShell:

```powershell
python scripts/configure_runtime_secrets.py
docker compose build assistent document-worker consultant webchat
docker compose up -d postgres qdrant
```

Linux:

```sh
python3 scripts/configure_runtime_secrets.py
docker compose build assistent document-worker consultant webchat
docker compose up -d postgres qdrant
```

Генератор заполняет только отсутствующие/пустые значения ключей и runtime-паролей, не печатает их. `.env` не коммитится. Дождитесь готовности PostgreSQL, затем выполните миграции под прежней учётной записью развёртывания из `.env` (команды подходят PowerShell и обычному shell):

```sh
docker run --rm --network viio_viio_net --env-file .env -e POSTGRES_HOST=postgres -e POSTGRES_PORT=5432 -e POSTGRES_DB=agent_db -v "${PWD}/Documents/scripts:/migration:ro" viio-documents:latest python /migration/migrate_schema.py
docker run --rm --network viio_viio_net --env-file .env -e POSTGRES_HOST=postgres -e POSTGRES_PORT=5432 -e POSTGRES_DB=agent_db -v "${PWD}/Assistent/scripts:/migration:ro" viio-assistent:latest python /migration/migrate_schema.py
docker run --rm --network viio_viio_net --env-file .env -e POSTGRES_HOST=postgres -e POSTGRES_PORT=5432 -e POSTGRES_DB=user_db -e DATABASE_URL= -e DATABASE_MIGRATIONS_ENABLED=true viio-webchat:latest node --input-type=module -e "import {initDb,getPool} from './dist-server/db.js'; const ok=await initDb(); await getPool().end(); if(ok===false)process.exit(1);"
docker run --rm --network viio_viio_net --env-file .env -e POSTGRES_HOST=postgres -e POSTGRES_PORT=5432 -v "${PWD}/Documents/scripts:/migration:ro" viio-documents:latest python /migration/provision_runtime_roles.py
```

Имя сети/томов выше соответствует стандартному Compose project `viio`. При другом имени используйте соответствующие имена. Для файлового тома при первом запуске под UID 65532:

```sh
docker run --rm --user 0:0 -v viio_documents_storage:/data/documents viio-documents:latest chown -R 65532:65532 /data/documents
docker compose -f docker-compose.yml -f docker-compose.prod.yml up -d --no-build document-worker documents assistent consultant webchat
```

Для локальной диагностики вместо последней команды можно использовать основной Compose без production override. Веб-интерфейс: http://localhost:3000. Создание пользователей, загрузка файлов и публикации выполняются администратором через WebChat. Параметры BOOTSTRAP_ADMIN_USERNAME/PASSWORD создают только первого администратора и не перезаписывают существующего.

Для OCR включите профиль pdf после сборки PDF-worker и подготовки отдельного тома моделей под UID 65532. Без этого обычные текстовые PDF/DOCX/ODT обрабатываются worker, а сканы потребуют OCR.

## Переход существующей установки и откат

Перед обновлением сохраните PostgreSQL agent_db/user_db и файловый том. Новые роли можно выдать заранее, до остановки приложений. Не удаляйте старые учётные записи и тома. Сохраните предыдущие image ID/теги перед заменой образов; выполните коммит перед обновлением контейнеров. Переключение ключей и закрытие портов требует согласованного обновления клиентов.

Откат приложения не требует изменения документов: верните сохранённые образы и согласованные прежние настройки подключения/ключей. Для Qdrant при возврате прежней конфигурации учитывайте включённую аутентификацию. Восстановление данных из резервной копии выполняется отдельно только при повреждении данных. `docker compose down -v` запрещён для этого перехода: он удалит постоянные тома.

## Проверки выпуска

Выпуск применён 28 октября 2026 года после коммита `79c1822`. Проверка реального запуска обнаружила остаточную инициализацию встроенного консультанта при старом CONSULTANT_ENABLED=true; она удалена отдельным коммитом `aac6547` до повторного обновления Assistent. Добавлен регрессионный тест этой комбинации окружения.

- Полный Python-набор: **305 passed**; после исправления запуска дополнительно прошёл новый целевой регрессионный тест. Тесты используют отдельные схемы PostgreSQL и векторы в памяти.
- В Docker-сборке WebChat: **78 passed**, production-сборка прошла. Локальный Windows-прогон части старых proxy-тестов не смог выполнить loopback fetch; приёмочным для этих сценариев является успешный Linux/Docker-прогон.
- Собраны независимые образы. В Documents нет пакета assistent; в Assistent нет viio_documents и qdrant_client. Локальные размеры: Assistent **359 MB** вместо 500 MB, Documents **461 MB** вместо 500 MB, WebChat **324 MB**. Время сборки не оценивалось как benchmark.
- Все восемь сервисов healthy, WebChat `/health` возвращает `db: true`. Фактический UID приложений — 65532 либо node; root filesystem read-only, capabilities сброшены. На хост опубликованы только WebChat 3000 и Consultant 8001. Внутренние PostgreSQL/Qdrant/Assistent/Documents host ports отсутствуют.
- Живые проверки ключей: read не может загружать; source не открывает каталог; admin не авторизуется в worker; read не авторизуется в чате; анонимный запрос отклонён. Qdrant требует ключ и запрещает изменение коллекции с readonly-ключом.
- Четыре runtime-роли PostgreSQL реально не имеют superuser/createdb/createrole. Assistent не читает documents, Documents API не читает user_facts и не изменяет documents; worker и WebChat имеют необходимые права записи своих таблиц.
- Через работающий API загружен собственный приватный DOCX, скачивание employee отклонено, admin получил точные оригинальные байты. Опубликован разрешённый фрагмент без приватного canary; новая версия унаследовала ACL и закрыла прежнюю публикацию. Все собственные проверочные версии, файлы, задания и публикации удалены по отдельному owner/id; постоянные записи не затрагивались.
- Контрольные суммы **49** сохранённых файлов совпали. До/после проверки: **79 версий / 75 активных / 43 публикации**.
- Основной агент и Consultant ответили на обычный вопрос про поиск электронного рецепта по СНИЛС, без указания инструментов, и вернули источники. Это проверка работоспособности и происхождения материалов, а не полная оценка фактологической точности: основной агент добавил категоричное «нельзя напрямую», которое требует проверки источниками на этапе B.
- Выполнен полный путь Documents → worker → Docling CPU под non-root на синтетическом скане. HTTP 200, engine docling-cpu, 1 страница; распознаны смысловая строка и номер 2026. Латинская аббревиатура VIIO распознана ошибочно как кириллическая: ручная проверка OCR по-прежнему необходима; PDF-очередь сохраняет этап подтверждения текста.

Резервные копии agent_db/user_db и оригиналов сохранены в игнорируемом `data/backups/release-a-2026-10-28`. Архив agent_db успешно восстановлен в отдельную временную базу с проверкой 79/75/43; временная база удалена. Стандартный пароль администратора развёртывания заменён случайным; новый находится только в локальном `.env`. Сервисы не используют эту привилегированную учётную запись. Пользовательские пароли/сессии не сбрасывались.

SQL MCP profile сейчас выключен: его внешний datasource в этом выпуске не подключался. Стартап теперь проверяет, что настроенный PGSQL_USER не является привилегированной ролью и не имеет CREATE/табличных прав записи, в дополнение к restricted/read-only режиму. Это не заменяет выдачу SELECT только на разрешённые таблицы внешней тестовой БД.
