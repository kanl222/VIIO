# Готовые компоненты агента

## Что внедрено

- `langchain.agents.create_agent` выполняет цикл модели и инструментов.
  Внешний граф VIIO сохраняет полный чекпоинт, изоляцию области доступа,
  суммаризацию LangMem и совместимость формата истории.
- `ToolCallLimitMiddleware`: до трёх вызовов инструментов на ход, включая
  параллельные вызовы. Следующий ход получает новый бюджет.
- `ModelRetryMiddleware`: до двух повторов при временных сетевых ошибках,
  rate limit и ошибках сервера OpenAI-совместимого провайдера. Ошибки прав и
  валидации не повторяются. Повторы HTTP-клиента провайдера могут действовать
  дополнительно; общий таймаут специалиста остаётся верхней границей.
- `ToolRetryMiddleware`: один повтор при транспортной ошибке или таймауте
  инструмента. После исчерпания повторов возвращается безопасное сообщение.
  Инструменты, возвращающие текст ошибки, повторно не выполняются.
- `langchain.mcp.MCPAdapter` заменяет ручное создание MCP-сессий GitHub и
  PostgreSQL. Сохранены фиксированные списки разрешённых инструментов,
  роли, выбранный репозиторий и ограничения SQL. До открытия сессии проверяются
  права. Для транспорта MCP предусмотрен один повтор сетевой ошибки через
  готовый `Runnable.with_retry` в пределах общего таймаута.
- `AsyncPostgresStore` хранит пользовательские факты вместо собственной таблицы.
  Namespace включает владельца и хэш области доступа. Команды `/remember`,
  `/facts`, `/forget`, ограничение 100 фактов на пользователя и проверка секретов
  сохранены. Запоминание остаётся явным действием пользователя.

MCPAdapter пока beta. Используемые версии зафиксированы в `Assistent/uv.lock`;
MCP SDK обновлён до 2.x, FastMCP — до 4.x. Проверен настоящий обмен с локальным
MCP-сервером в памяти; подключение к рабочим GitHub и PostgreSQL требует
настроенных реквизитов и отдельной проверки в вашем окружении.

## Перенос пользовательских фактов

Если `DATABASE_MIGRATIONS_ENABLED=true`, настройка Store и перенос выполняются
при запуске сервиса. В production эта настройка обычно выключена. Перед запуском
новой версии выполните отдельную миграцию:

1. Остановите старый Assistent, чтобы он не записывал факты во время переноса.
2. Подготовьте новое окружение / образ Assistent.
3. С реквизитами миграционной роли в переменных `POSTGRES_*` выполните:

   ```powershell
   python -m assistent.utils.migrate_personal_memory
   ```

   Роль должна иметь права создания таблиц в базе Assistent и чтения старой
   `user_facts`. Runtime-роли нужны SELECT/INSERT/UPDATE/DELETE на `store`;
   существующие права на `user_facts` сохраняются для удаления старой копии факта.
4. Запустите новый Assistent с обычной runtime-ролью.

Миграция сохраняет UUID, владельца, область доступа, источник и дату. Старую таблицу
не удаляет. Маркер миграции исключает повторный импорт и восстановление забытых
записей. `/forget` атомарно удаляет факт из Store и его старую копию, если она есть.
Миграция рабочей БД в рамках изменения кода не запускалась.

## Проверки

Запускайте тесты из каталога Assistent, чтобы корневой рабочий `.env` не подменял
тестовые параметры авторизации:

```powershell
cd Assistent
python -m pytest tests -q -p no:cacheprovider
```
