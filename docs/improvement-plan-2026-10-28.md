# План улучшения VIIO — 28 октября 2026

Проверены текущие исходники и Docker-конфигурация, размеры локальных образов и версия работающего Qdrant (1.20.0). Это план изменений и статическая проверка рисков перед релизом; нагрузочные испытания, сканирование уязвимостей зависимостей и новый прогон ответов моделей в эту проверку не входили. Настройки окружения с секретами не выгружались. Последний функциональный прогон: 282 Python-теста и 78 веб-тестов; он не заменяет проверки ниже.

## Применённые навыки и ограничения

Прочитаны `langgraph-fundamentals`, `rag-implementation`, `security-best-practices` с рекомендациями для FastAPI, Express и React, а также `qdrant-advisor` с актуальным руководством Qdrant по hybrid retrieval. Запрошенные `senior-devops`, `rag-architect`, `senior-security` не найдены среди локальных навыков. Их применение не заявляется; Docker проверен непосредственно по проекту и официальным рекомендациям. Gemini/agy-delegator в доступных инструментах не обнаружен, анализ выполнен локально без делегирования.

## Что уже работает и должно сохраниться

- Отдельные процессы Assistent, Consultant, Documents и document-worker; разбор Office выполняется в worker на CPU.
- Асинхронный RPC поиска; параллельные private semantic, PostgreSQL lexical и public semantic ветки в `EnhancedRetrieval.search`.
- PostgreSQL FTS с GIN и словарями russian/simple уже существует. Полное сканирование всех документов для каждого запроса предлагать не нужно.
- Публичная коллекция содержит явно одобренные снимки; Consultant проверяет актуальность публикаций повторно после генерации. Частный оригинал и опубликованный фрагмент имеют разные правила выдачи.
- Ограничения вызовов инструментов, контекста, очистка источников ответа; код доступен programmer/admin. Coder пишет код текстом и не получает инструменты выполнения или создания файлов.
- Multi-stage сборки Python/WebChat, отдельные слои зависимостей, lock-файлы и исключение данных/секретов из контекста сборки уже есть.

## 1. Перед релизом: границы доступа

### SEC-01 — High: небезопасное поведение при отсутствии межсервисного ключа

**Доказательство:** `Assistent/src/assistent/router.py:196` — `verify_internal_token` проверяет запрос только внутри `if settings.internal_api_key`; при пустом ключе зависимость пропускает запрос. У `documents_client.py:11` уже есть более строгий `require_internal`, отклоняющий пустую настройку. Разные маршруты защищены неодинаково.

**Влияние:** при запуске с пустым ключом доступ к части внутренних маршрутов может открыться без аутентификации. Чат принимает доверенный `user_context`, поэтому эта граница особенно важна. Это подтверждённое свойство кода, а не утверждение, что рабочий ключ сейчас пустой.

**Изменение:** единая fail-closed проверка для всех внутренних маршрутов и отказ production-запуска при отсутствующем/шаблонном ключе. Разделить полномочия: вызов агента, чтение знаний, управление документами, вызов worker. Ключ публичных материалов Consultant сохранить отдельным. Ротацию сделать с коротким переходным периодом, без потери активных заданий.

**Приёмка:** отсутствующий/неверный ключ отклонён; ключ поиска не может публиковать/удалять/загружать документы; ключ Consultant не может обращаться к внутреннему каталогу; подмена role/owner/departments через браузер не меняет доверенный контекст. WebChat уже берёт контекст из сессии (`server/routes/chatRoutes.ts:90`); сохранить это поведение.

### SEC-02 — High при доступности хоста извне: лишние опубликованные порты и общие учётные данные

**Доказательство:** `docker-compose.yml:9` публикует PostgreSQL, `:27` — Qdrant REST/gRPC, `:108` — Documents; Assistent тоже имеет host port. Адрес привязки в этих записях не ограничен localhost. Конфигурация использует один POSTGRES_USER для нескольких приложений и допускает стандартные значения пользователя/пароля. Внешний firewall и реальные значения окружения в этом обзоре не проверялись.

**Изменение:** отдельный production Compose override: наружу только требуемые входы WebChat/Consultant через настроенный gateway; внутренним сервисам оставить Docker DNS. Для локальной разработки привязать диагностические порты к 127.0.0.1. Отдельные роли PostgreSQL по сервисам, миграции отдельной ролью, readonly-роль для SQL-инструмента. Проверить Qdrant API authentication и доступ по сетям. Не менять и не удалять volumes.

**Приёмка:** таблица разрешённых сетевых соединений; снаружи внутренние порты недоступны; приложение не имеет прав superuser; SQL-инструмент не выполняет записи. Отдельно проверить существующую инфраструктурную защиту, прежде чем объявлять эксплуатационную уязвимость.

### SEC-03 — Medium: ограниченная изоляция процессов

**Доказательство:** Consultant уже имеет `USER`, `read_only`, `cap_drop` и `no-new-privileges`. В `Assistent/Dockerfile:19`, `Documents/Dockerfile:12` и `pdf-worker/Dockerfile:1` финальные стадии не задают непривилегированного пользователя. Эти сервисы не имеют аналогичного полного набора ограничений в Compose.

**Изменение:** non-root, drop capabilities, no-new-privileges; read-only root filesystem с отдельными writable volumes/tmpfs по фактическим нуждам. Для worker сохранить запись оригиналов, для Docling — моделей и временных файлов. Добавить разумные pids/memory/CPU limits после замеров.

**Приёмка:** загрузка, новая версия, публикация, OCR, перезапуск и скачивание работают под non-root; записи вне разрешённых директорий запрещены.

### SEC-04 — проверка перед выпуском: отзыв прав в длинном диалоге

В `graph_builder.py:44` граница истории зависит от user_id/role/departments. Изменение ACL самого документа без изменения этих полей не меняет scope. Это ещё не доказанная утечка: нужны специальные сценарии проверки старых ToolMessage, ответа модели и сводки.

Проверить отзыв публикации/ACL между поиском и генерацией, между двумя сообщениями и после суммаризации. Для основного агента предусмотреть проверку актуальных document/version/ACL перед передачей старого контекста модели; при необходимости очищать зависимые сводки и результаты. Отдельно проверить все скачивания, версии, задания очереди и повторное выполнение по чужому идентификатору. Без успешной матрицы ролей релиз не принимать.

## 2. Измерения до оптимизации

Сначала восстановить доступ к серверу моделей/эмбеддингов и проверить его из нужных контейнеров. Разделить liveness приложения и readiness зависимостей; сбой модели должен давать понятный ограниченный по времени ответ.

Собрать 60–100 рабочих вопросов с ожидаемыми документами/версиями и выдержками: инструкции организации, аббревиатуры, точные имена методов/SQL, перефразирования, опечатки, уточнение предыдущего вопроса, отсутствующие сведения, конфликт версий, частные документы и опубликованные фрагменты. Consultant и основной агент оценивать отдельно; приёмочные вопросы формулировать без подсказки инструмента.

Измерять Recall@5/MRR поиска, подтверждённость утверждений, точность источников, корректные отказы, нарушения ACL, число LLM/tool вызовов, токены, p50/p95 поиска и полного ответа. Трассировка по request ID: embedding, PostgreSQL, private/public Qdrant, объединение, модель, очередь. Сырые документы, пароли и персональные данные в трассы не писать.

## 3. Docker: сначала быстрые изменения, затем разделение зависимостей

Текущие локальные размеры по `docker images` (не размер скачивания): Assistent 500 MB, Documents 500 MB, Consultant 300 MB, WebChat 324 MB, PDF worker 2.97 GB. Общие слои нельзя считать несколько раз при оценке занятого диска. Время сборки сейчас не измерялось.

1. Зафиксировать версии/digest базовых Python/Node/uv/Qdrant образов и порядок обновления. Убрать зависимость от плавающих `latest` в воспроизводимом релизе.
2. BuildKit cache mounts для uv/npm/pip; npm cache не оставлять в финальном runtime. Сохранить существующий порядок COPY lock-файлов до исходников и строгие dockerignore. Для CI отдельно настроить layer cache; cache mounts и удалённый cache не считать одним механизмом.
3. Перенести `pytest` из production dependencies (`Assistent/pyproject.toml:28`) в dev. Разделить runtime extras/groups для агента и обработки документов: Assistent не должен ставить Office-парсеры и Qdrant-клиент только потому, что делит пакет с Documents. Перед разделением проверить eager imports и сборку каждого профиля.
4. Убрать дублирование Dockerfile Assistent/Documents через общие именованные стадии, сохранив отдельные финальные images и процессы. Documents и worker уже используют один образ — сохранять это, пока нет измеримой причины разделить.
5. В WebChat разделить browser-build и server runtime dependencies; React, иконки и полный пакет assets не нужны серверу после формирования dist, если runtime imports это подтверждают. Отдельный dependency stage с production-only установкой предпочтительнее копирования полного node_modules.
6. Для Docling сохранить отдельный optional profile и CPU torch. Зафиксировать зависимости; сначала измерить состав пакетов и необходимость torchvision/OCR-компонентов. Удалять их только после DOCX/ODT/PDF/OCR регрессии. Не обещать уменьшение 2.97 GB в несколько раз без анализа.
7. CI запускает тесты до выпуска immutable image; быстрая production-сборка может использовать отдельную test-stage, но не обходить обязательные проверки. Коммит перед каждым обновлением контейнеров.

Приёмка: cold build, warm build, изменение только исходника, изменение dependency lock; время и размер до/после. Предварительная цель для warm source-only build — ускорение минимум на 30%, размер основных runtime — снижение минимум на 15%; подтвердить измерениями, не считать обещанным результатом. Все тесты и чистая сборка без локальных игнорируемых assets обязательны.

## 4. LangGraph/RAG: точность без лишних модельных проходов

1. Сохранить самостоятельный выбор инструментов моделью и fallback поиска по организационным вопросам. Приветствия, арифметика и переформулирование не должны платить за retrieval. Coder вызывается только для programmer/admin; при нужде получает разрешённые знания до написания кода.
2. Выделить явные результаты этапов: найденные материалы с id/version, ранги, текущий бюджет инструментов/токенов, состояние ошибки. Формировать текст промпта на входе модели; не превращать всё состояние в повторяющиеся длинные строки. Не хранить секретные извлечённые тексты в долговременной памяти без политики удаления/отзыва.
3. В `EnhancedRetrieval` (`enhanced_retrieval.py:13`) текущая итоговая сортировка основана на совпадениях слов, названия и имени файла. Сравнить её с RRF существующих PostgreSQL FTS и dense списков, сохранив исходные ранги и разнообразие документов. Это первый эксперимент; дополнительная sparse-коллекция для него не нужна.
4. Альтернативой отдельным экспериментом проверить BM25+dense Query API в установленном Qdrant 1.20.0. Не заменять сразу работающий PostgreSQL FTS; для русского текста и кода нужны отдельные настройки и проверка качества. Перенос всего retrieval в Qdrant оправдан только выигрышем по качеству/задержке/сопровождению.
5. Структурные чанки: заголовки/абзацы/таблицы документов, функции/классы/пути для кода. Сохранять ссылку на оригинал и доступную версию. Подмешивать соседний фрагмент только при необходимости; лимитировать контекст токенами конкретной модели. Существующий корпус мигрировать через теневой индекс с откатом.
6. Один ограниченный query rewrite только при слабой выдаче или уточнении беседы; reranker включать после A/B-замеров на небольшом candidate pool. Дополнительные вызовы модели на каждый вопрос по умолчанию не добавлять.
7. Переиспользовать lifecycle HTTP-клиенты вместо создания нового в каждом поиске (`documents_client.py:28`). Отдельные deadline для retrieval branches и всего запроса; `gather` сейчас ждёт завершения всех веток. Возвращать помеченную частичную выдачу при сбое одной ветки и честный отказ при отсутствии доказательств.
8. Проверить, не вычисляется ли один query embedding дважды для private/public dense поиска. Переиспользовать только при совпадении модели, версии, нормализации и размерности. Кэш текстовых выдач вводить только с учётом ACL, версии и немедленного отзыва; сначала достаточно кэша query embeddings без документов.
9. Пользователь получает названия документов и разрешённые ссылки/версии. chunk_id, payload, внутренние промпты и служебные счётчики не должны попадать в ответ. Проверку подтверждённости выполнять по тестовой разметке; не добавлять обязательную LLM-проверку каждого ответа без замера задержки.

Приёмка: ноль утечек в проверенной матрице доступа; Recall@5 не ниже baseline, целевой уровень ≥90% на размеченной выборке; точность источников ≥95%; p95 retrieval не хуже baseline, целевой выигрыш ≥20% на том же оборудовании. Качество на тестах и production-нагрузке различать.
