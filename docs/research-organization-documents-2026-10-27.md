# Документы и исходный код организации: дополнение к плану VIIO

Исследование первичных источников, 27 октября 2026. Здесь разделены возможности готовых компонентов и предложения для VIIO. Это не внедрение: код приложения и рабочие данные не менялись. Отдельные материалы по исходникам: [исследование кода организации](research-organization-code-2026-10-27.md).

## Главный вывод

Следует разделить оригинал, структурированное представление и поисковый индекс. Для документов полезны страницы, заголовки и таблицы; для исходников — репозиторий, commit, файл и символ. Пользователь видит источник и доступный оригинал, а внутренние номера чанков остаются диагностикой. Это предлагаемая архитектура VIIO на основе возможностей, перечисленных далее.

## 1. Сохранять структуру после распознавания

DoclingDocument представляет текст, таблицы, изображения, иерархию разделов, происхождение элементов и координаты, когда они доступны. Поэтому полезно сохранять его структурированный результат вместе с оригиналом, а Markdown использовать как дополнительное представление. [DoclingDocument](https://docling-project.github.io/docling/concepts/docling_document/).

В текущем `pdf-worker/app.py` результат преобразуется через `export_to_markdown()`. API получает текст, число страниц и название движка; связь конкретного фрагмента со страницей через эту цепочку не передаётся. Это наблюдение по коду VIIO, а не ограничение Docling.

Docling имеет HierarchicalChunker и HybridChunker: второй сочетает структуру с ограничением размера по токенам. Можно сохранять метаданные и контекст заголовков, проверять разбиение таблиц. Это отличается от текущего разрезания произвольного текста в DocumentService. [Docling: Chunking](https://docling-project.github.io/docling/concepts/chunking/).

Предложение: хранить `original`, структурированный JSON, Markdown и версию обработчика. Для каждого поискового фрагмента — внутреннюю ссылку на версию и доступные страницы/разделы. Не придумывать номера страниц у TXT/Markdown и других форматов без страниц. Новую стратегию сравнить на русских инструкциях, SQL-примерах, таблицах и сканах; универсальный размер фрагмента из документации не следует.

## 2. Использовать готовый асинхронный сервер конвертации

**docling-serve** уже предоставляет асинхронную загрузку, опрос состояния, WebSocket статусов и получение результата. Основные маршруты: `/v1/convert/file/async`, `/v1/status/poll/{task_id}`, `/v1/result/{task_id}`. [REST API](https://docling-project.github.io/docling/usage/api_server/rest_api/).

Сервер поддерживает локальный движок и Redis/RQ с отдельными процессами обработки; есть настройки CPU. Это кандидат на замену самописной HTTP-обёртки вокруг Docling, а не автоматическая замена всей системы управления документами. [Развёртывание](https://docling-project.github.io/docling/usage/api_server/deployment/), [конфигурация docling-serve](https://github.com/docling-project/docling-serve/blob/main/docs/configuration.md).

Для VIIO нужно отдельно сохранить пакет загрузки, пользователя, права, оригиналы и журнал обработки. Не считать локальную очередь в памяти устойчивой к перезапуску. Результат конвертации следует забрать в постоянное хранилище: очередь и временный результат не являются библиотекой документов. Версии сервера, библиотеки и формата JSON фиксировать и проверять совместно.

Пакетная конвертация Docling различает успех, частичный успех и ошибку. Частично распознанный документ нельзя молча объявлять полностью готовым. [Официальный пример batch conversion](https://docling-project.github.io/docling/_generated/examples/batch_convert/).

## 3. Очередь должна выдерживать повторный запуск

FastAPI рекомендует для тяжёлых фоновых вычислений рассматривать отдельные системы задач, например Celery. Простого выполнения после HTTP-ответа недостаточно для требований устойчивой массовой обработки. [FastAPI Background Tasks](https://fastapi.tiangolo.com/tutorial/background-tasks/).

Celery документирует повторное выполнение задач, необходимость идемпотентности, retry и особенности `acks_late`. Позднее подтверждение не гарантирует повтор в любом сценарии завершения процесса и не создаёт семантику exactly-once. [Celery Tasks](https://docs.celeryq.dev/en/stable/userguide/tasks.html).

Предложение: для конвертации сначала оценить встроенный RQ-вариант docling-serve. Celery добавлять, только если нужен единый оркестратор для дополнительных этапов. Не вводить две очереди без необходимости. Нужна проверка фактического восстановления выбранной конфигурации Redis/worker.

Задание VIIO привязывать к версии файла и версии обработки. Повтор не должен создавать копии чанков. Дедупликацию учитывать в пределах организации и прав; одинаковое содержимое не означает одинаковую видимость. Состояния: сохранён → в очереди → извлекается → требует проверки/индексируется → готов либо ошибка. Новая версия становится активной после успешной индексации; незавершённый индекс не должен участвовать в ответах. Это проектная политика, её должен обеспечивать код приложения.

## 4. Хранение оригиналов и выдача

S3 Versioning умеет сохранять и восстанавливать версии объектов. Каждая версия хранится целиком; versioning сам по себе не является отдельной резервной копией приложения. [Amazon S3 Versioning](https://docs.aws.amazon.com/AmazonS3/latest/userguide/Versioning.html).

Для начала VIIO может использовать локальный постоянный том с неизменяемыми ключами версий и резервным копированием. Интерфейс хранилища стоит отделить от логики документов, чтобы позднее подключить проверенный S3-совместимый сервер. Документация AWS не гарантирует идентичность всех функций стороннего S3-сервера; совместимость проверяется отдельно. Облачный AWS для этого плана не обязателен.

Presigned URL предоставляет доступ владельцу ссылки до истечения срока и обычно допускает повторное использование. Это не проверка роли текущего пользователя VIIO. [Amazon S3: Presigned URLs](https://docs.aws.amazon.com/AmazonS3/latest/userguide/using-presigned-url.html).

При требовании проверки прав на каждом скачивании предлагаю авторизованный маршрут VIIO, передающий файл пользователю. Альтернатива — краткоживущая подписанная ссылка после проверки доступа, с явным принятием окна её действия. Проверять нужно конкретную версию документа; название файла не использовать как произвольный путь на диске.

## 5. Единые права на поиск и файлы

Документация Azure AI Search описывает фильтры документов по идентификаторам пользователей/групп, применяемые во время поиска. Это полезный образец, не рекомендация переходить на Azure; некоторые встроенные механизмы Microsoft отмечены preview. [Document-level access control](https://learn.microsoft.com/en-us/azure/search/search-document-level-access-overview).

Для VIIO предлагаю одну политику для списка документов, поиска, предпросмотра, скачивания, исторических версий и справки coder. Доступ к модели coder не должен автоматически давать доступ ко всем репозиториям организации. Поиск исходников разрешать только programmer/admin и в пределах разрешённых проектов. Закрытый текст не должен попадать в промпт до решения о доступе. Старые документы в истории и кэшах также учитывать при изменении прав.

## 6. Как показывать источники без утечки служебных полей

Предлагаемый пользовательский вид:

- Документ: «Инструкция SSRS», версия 3, страница 12, раздел «Параметры», кнопка открытия оригинала.
- Код: `ReportService.cs`, метод `BuildReport`, строки 80–105, commit; ссылка на конкретную версию файла.

GitHub поддерживает постоянные ссылки на строки конкретного commit. Ссылка на ветку не фиксирует версию исходника. [GitHub: Permanent code snippet links](https://docs.github.com/en/get-started/writing-on-github/working-with-advanced-formatting/creating-a-permanent-link-to-a-code-snippet).

Внутренние `chunk_index`, ID точки Qdrant, оценки сходства и XML-теги не являются пользовательским источником. Публичный контракт ответа VIIO должен содержать отдельные `answer` и `sources`; реальные названия и адреса оформляет сервер. Если модель выбирает ссылки по коротким меткам, сервер сверяет их с разрешённым набором. Валидный ID ещё не доказывает, что фрагмент подтверждает утверждение. «Предоставленные материалы» и «источник конкретного утверждения» следует различать.

## Что добавить к плану реализации

1. Каталог документов и версий, оригиналы, журнал обработки, единые права.
2. Массовая загрузка: пакет с независимым статусом каждого файла, ограничение числа CPU-задач, повторы и восстановление.
3. Проверка docling-serve как готового конвертера; сохранение структурированного результата и географии источников.
4. Отдельная обработка исходников с привязкой к commit; детали в исследовании кода.
5. Серверные карточки источников и скачивание; скрытие внутренней диагностики.
6. Испытания удаления, смены прав, устаревшей версии, повторной обработки и частичного распознавания. Дополнительно — поиск по содержимому, таблицам и именам символов.

Не проверено в этом исследовании: скорость docling-serve на оборудовании пользователя, совместимость с установленной версией Docling и точность нового разбиения. Это критерии отдельного прототипа. Полноценная DMS, GraphRAG и новый брокер не требуются до появления подтверждённой задачи для них.
