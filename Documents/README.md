# Общий сервис документов VIIO

Два процесса обслуживают общую базу основного агента `assistent` и внешнего консультанта:

- `documents` — HTTP API, порт 8002: каталог, версии, права, загрузка, скачивание, состояние заданий, поиск и утверждённые публикации.
- `document-worker` — обработка очереди, распознавание файлов через существующий PDF worker, индексация и восстановление индексов. Порт наружу не публикуется.

Поддерживаются PDF, DOCX, ODT, TXT, Markdown и разрешённые исходники. DOCX/ODT разбираются на CPU в worker без сервера моделей. Извлекаются основной текст, списки, таблицы и адреса гиперссылок. Автоматическая нумерация сложных списков упрощается до маркеров; изображения и сканы внутри Office не распознаются. Для них используйте PDF/OCR.

Очистка новых DOCX/ODT/PDF и TXT-загрузок убирает повторные пробелы, табуляцию и отступы обычного текста, лишние пустые строки, BOM, неразрывные пробелы, мягкие переносы и служебные невидимые символы. Цифры, пунктуация, абзацы, списки, таблицы и ссылки сохраняются. Исходники кода, Markdown и вручную введённый текст не проходят такую очистку. Оригинальные байты файлов не изменяются.

Массовая загрузка (в том числе один файл) и новая версия сохраняют исходный DOCX/ODT с правильным MIME. В форме «Новый документ» файл используется для предварительного извлечения текста; результат можно отредактировать и сохранить как текстовый документ. Для сохранения Office-оригинала используйте массовую загрузку. Предпросмотр `POST /api/v1/documents/extract-office?filename=example.docx` не индексирует документ и требует межсервисного ключа.

Тяжёлые запросы создания текста и публикации передаются API в worker по HTTP с прежним форматом ответа. Массовая загрузка возвращает `202` и идентификаторы заданий; их состояние хранится в существующей очереди PostgreSQL. Лимит обработки `BULK_MAX_WORKERS` общий для очереди, прямой индексации и публикаций; по умолчанию один. Периодическая синхронизация публичного индекса использует тот же лимит.

Оригиналы остаются в прежнем Docker-томе `documents_storage`, каталог и задания — в `agent_db`, индексы — в прежних коллекциях Qdrant. Перенос/повторная загрузка 75 документов не требуется. Приложения используют одну библиотеку доменных моделей из `Assistent/src/assistent`; Docker-образ документов собирается независимо по этому Dockerfile. Копий бизнес-логики нет.

`assistent` не запускает очередь, не создаёт клиент эмбеддингов/Qdrant и не монтирует оригиналы. Его поиск — асинхронный HTTP-инструмент `POST /api/v1/knowledge/search`, с серверным контекстом пользователя и межсервисным ключом. Личные факты не передаются в поиск. Поиск не переключается на локальную базу при ошибке сервиса.

Консультант обращается напрямую к Documents API и использует только `/api/v1/consultant-materials/search` и `/validate` с отдельным `X-Publication-Key`. Ключ источника не открывает каталог, оригиналы или внутренний поиск. Публикации остаются явными утверждёнными снимками, их актуальность проверяется после ответа модели. Правило `is_public` внутри организации не означает внешнюю публикацию.

## Docker: Windows и Linux

Из корня проекта:

```sh
docker compose up -d --build
docker compose --profile pdf up -d --build pdf-worker
docker compose ps
```

Основной агент: `http://localhost:8000`; консультант: `http://localhost:8001`; документы: `http://localhost:8002`. Все операции с документами требуют доверенного межсервисного ключа, кроме служебной проверки здоровья. Веб-чат использует `ASSISTENT_URL` и `DOCUMENTS_URL`; прежняя `AGENTAI_URL` поддерживается для совместимости. Старые адреса `/api/v1/documents/...` на порту 8000 работают как потоковый прокси без локальной обработки и сохранения файлов в агенте.

При первом переходе с прежнего Compose остановите контейнер `viio_apiagent`, чтобы освободить порт 8000, затем запустите новый Compose. Не удаляйте тома (`down -v` уничтожает данные). Консультант зависит от готовности Documents API, а не от основного агента.

## Локальные процессы без Docker

Сохраните настройки подключения к PostgreSQL, Qdrant и моделям. Из каталога `Assistent` установите зависимости `uv sync`. Запустите три отдельных терминала.

PowerShell:

```powershell
# Терминал 1 — worker
$env:SERVICE_ROLE='document-worker'
uv run uvicorn assistent:create_app --factory --port 8003
# Терминал 2 — Documents API
$env:SERVICE_ROLE='documents'
$env:DOCUMENT_WORKER_URL='http://localhost:8003'
uv run uvicorn assistent:create_app --factory --port 8002
# Терминал 3 — основной агент
$env:SERVICE_ROLE='assistent'
$env:DOCUMENTS_URL='http://localhost:8002'
uv run uvicorn assistent:create_app --factory --port 8000
```

Linux (каждая команда в отдельном терминале):

```sh
SERVICE_ROLE=document-worker uv run uvicorn assistent:create_app --factory --port 8003
SERVICE_ROLE=documents DOCUMENT_WORKER_URL=http://localhost:8003 uv run uvicorn assistent:create_app --factory --port 8002
SERVICE_ROLE=assistent DOCUMENTS_URL=http://localhost:8002 uv run uvicorn assistent:create_app --factory --port 8000
```

Для обоих процессов документов укажите одинаковый абсолютный `DOCUMENTS_STORAGE_PATH`. В локальном окружении консультанта задайте `CONSULTANT_SOURCE_URL=http://localhost:8002`. Интерфейс пользователей, создание администратора и загрузка файлов в веб-чате сохраняются.

CPU и память обработки отделены от агентов. Общий сервер моделей и общая БД всё ещё могут испытывать нагрузку, поэтому отдельные процессы сами по себе не гарантируют неизменную задержку ответов; для этого нужен нагрузочный прогон.

В Docker для `document-worker` по умолчанию заданы `DOCUMENT_WORKER_CPUS=1` и `DOCUMENT_WORKER_MEMORY=2g`. Настройки ограничивают потребление обработчика; существующий PDF worker сохраняет собственные ограничения.

Доверенный импорт бинарных материалов и ручную синхронизацию индекса запускайте только в `viio_document_worker`. Например:

```sh
docker cp Assistent/scripts/sync_public_index.py viio_document_worker:/tmp/sync_public_index.py
docker exec viio_document_worker python /tmp/sync_public_index.py
```
